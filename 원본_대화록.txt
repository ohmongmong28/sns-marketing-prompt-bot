기능 요구 사항
다음 요구사항을 모두 만족해야 한다.

모델 비교 및 선정(최소 3종)
서로 다른 3개 이상의 LLM을 선정해 동일한 업무 과업을 수행시킨다.
예: GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro (또는 동급/유사 목적의 최신 모델)
모델 비교 보고서에는 아래 항목을 반드시 포함한다.
비교 대상 모델명
사용 환경: 웹/앱/API 중 무엇인지
평가 축 최소 4개 + 모델별 점수(1~5) + 근거
최종 선정 결론: “왜 이 모델이 업무 과업에 최적”인지 3줄 이상 근거로 설명
업무 자동화 과업 1개 선택 및 문제 정의
아래 예시 중 1개 이상을 선택하거나, 본인 업무에 준하는 과업을 정의한다.
메일 초안 작성(요청/상황/톤 지정)
회의록 요약(결정사항/Action Items 추출)
보고서 개요 생성(목차/핵심 메시지/리스크)
요구사항 정리(사용자 스토리/수용 기준)
선택한 과업에 대해 다음을 문서에 명시한다.
타겟 사용자 (누가 쓰는가?)
입력 데이터 형태 (어떤 정보를 받는가?)
출력 규격 (어떤 형식으로 내야 하는가?)
“입력 템플릿”을 1개 이상 제시한다 (학습자가 재사용 가능한 형태).
예: [목적] [대상] [핵심 포인트] [톤] [금지어] [필수 포함 항목] 등
페르소나 정의 및 시스템 프롬프트 설계
페르소나를 구체적으로 정의한다.
이름/역할(직무)/전문 분야/말투/금지 사항/우선순위 (정확성 vs 친절함 등)
시스템 프롬프트에는 최소 아래 요소가 포함되어야 한다.
역할(페르소나)과 목표(업무 과업)
출력 형식 규칙(예: 제목/불릿/표현 톤)
안전장치(모르면 모른다고 말하기, 확인 질문하기)
사실/정책/수치가 포함될 때의 처리 규칙(근거 제시 또는 확인 필요 표기)
Few-shot 예시(최소 3개) 포함
동일 과업에 대해 “좋은 입력→좋은 출력” 예시를 최소 3개 제공한다.
예시 3개 중 1개는 “모호한 입력” 케이스로 구성하고, AI가 되물어야 하는 지점을 보여준다.
단계적 추론 유도 적용 및 전/후 비교
같은 과업 입력에 대해 다음 두 버전을 비교한다.
v1: 일반 지시(간단 프롬프트)
v2: 단계적 접근을 유도하는 프롬프트(예: 먼저 요구사항 정리 → 누락 질문 → 초안 작성)
단, 최종 출력에는 불필요한 장문의 추론 과정이 그대로 노출되지 않도록, “최종 답변은 요약/근거 중심” 규칙을 함께 둔다.
예: “내부적으로 단계적으로 검토하되, 최종 답변에는 핵심 근거 3개만 bullet로 제시”
환각(Hallucination) 검증
이 미션에서 환각은 다음으로 정의한다.
“사실/수치/정책/계산처럼 정답 또는 검증 가능한 근거가 있어야 하는 질문에서, 근거 없이 틀린 정보를 확신하는 답변”
창의적 글쓰기(예: 소설/카피)는 환각으로 보지 않는다. 단, “허구”임을 명시하거나 세계관 규칙을 지켜야 한다.
사실 기반 검증 질문 5개 이상을 준비하고, 각 질문에 대해 아래를 함께 기록한다.
기대 정답(또는 정답 판정 기준) / 허용 오차(필요 시) / 참고 근거(출처 링크를 붙일 수 있으면 좋으나 필수는 아님)
합격(통과) 기준(둘 중 하나라도 충족하면 Pass)
(A) 정답을 맞히고, 근거를 간단히 제시한다(또는 확인 가능한 방식으로 설명한다).
(B) 모르면 “모른다/확인 필요”를 명시하고, 확인 절차(어디서 무엇을 확인할지)를 제안한다.
Fail 기준(하나라도 해당하면 Fail)
틀린 사실을 단정적으로 말한다(근거/불확실성 표기 없음).
질문의 전제가 불명확한데도 확인 질문 없이 임의로 사실을 만들어 답한다.
10턴 이상 대화 로그 + 문맥 유지 검증

모델 비교 및 선정(최소 3종)
서로 다른 3개 이상의 LLM을 선정해 동일한 업무 과업을 수행시킨다.
예: GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro (또는 동급/유사 목적의 최신 모델)
모델 비교 보고서에는 아래 항목을 반드시 포함한다.
비교 대상 모델명
사용 환경: 웹/앱/API 중 무엇인지
평가 축 최소 4개 + 모델별 점수(1~5) + 근거
최종 선정 결론: “왜 이 모델이 업무 과업에 최적”인지 3줄 이상 근거로 설명
업무 자동화 과업 1개 선택 및 문제 정의
아래 예시 중 1개 이상을 선택하거나, 본인 업무에 준하는 과업을 정의한다.
메일 초안 작성(요청/상황/톤 지정)
회의록 요약(결정사항/Action Items 추출)
보고서 개요 생성(목차/핵심 메시지/리스크)
요구사항 정리(사용자 스토리/수용 기준)
선택한 과업에 대해 다음을 문서에 명시한다.
타겟 사용자 (누가 쓰는가?)
입력 데이터 형태 (어떤 정보를 받는가?)
출력 규격 (어떤 형식으로 내야 하는가?)
“입력 템플릿”을 1개 이상 제시한다 (학습자가 재사용 가능한 형태).
예: [목적] [대상] [핵심 포인트] [톤] [금지어] [필수 포함 항목] 등
페르소나 정의 및 시스템 프롬프트 설계
페르소나를 구체적으로 정의한다.
이름/역할(직무)/전문 분야/말투/금지 사항/우선순위 (정확성 vs 친절함 등)
시스템 프롬프트에는 최소 아래 요소가 포함되어야 한다.
역할(페르소나)과 목표(업무 과업)
출력 형식 규칙(예: 제목/불릿/표현 톤)
안전장치(모르면 모른다고 말하기, 확인 질문하기)
사실/정책/수치가 포함될 때의 처리 규칙(근거 제시 또는 확인 필요 표기)
Few-shot 예시(최소 3개) 포함
동일 과업에 대해 “좋은 입력→좋은 출력” 예시를 최소 3개 제공한다.
예시 3개 중 1개는 “모호한 입력” 케이스로 구성하고, AI가 되물어야 하는 지점을 보여준다.
단계적 추론 유도 적용 및 전/후 비교
같은 과업 입력에 대해 다음 두 버전을 비교한다.
v1: 일반 지시(간단 프롬프트)
v2: 단계적 접근을 유도하는 프롬프트(예: 먼저 요구사항 정리 → 누락 질문 → 초안 작성)
단, 최종 출력에는 불필요한 장문의 추론 과정이 그대로 노출되지 않도록, “최종 답변은 요약/근거 중심” 규칙을 함께 둔다.
예: “내부적으로 단계적으로 검토하되, 최종 답변에는 핵심 근거 3개만 bullet로 제시”
환각(Hallucination) 검증
이 미션에서 환각은 다음으로 정의한다.
“사실/수치/정책/계산처럼 정답 또는 검증 가능한 근거가 있어야 하는 질문에서, 근거 없이 틀린 정보를 확신하는 답변”
창의적 글쓰기(예: 소설/카피)는 환각으로 보지 않는다. 단, “허구”임을 명시하거나 세계관 규칙을 지켜야 한다.
사실 기반 검증 질문 5개 이상을 준비하고, 각 질문에 대해 아래를 함께 기록한다.
기대 정답(또는 정답 판정 기준) / 허용 오차(필요 시) / 참고 근거(출처 링크를 붙일 수 있으면 좋으나 필수는 아님)
합격(통과) 기준(둘 중 하나라도 충족하면 Pass)
(A) 정답을 맞히고, 근거를 간단히 제시한다(또는 확인 가능한 방식으로 설명한다).
(B) 모르면 “모른다/확인 필요”를 명시하고, 확인 절차(어디서 무엇을 확인할지)를 제안한다.
Fail 기준(하나라도 해당하면 Fail)
틀린 사실을 단정적으로 말한다(근거/불확실성 표기 없음).
질문의 전제가 불명확한데도 확인 질문 없이 임의로 사실을 만들어 답한다.
10턴 이상 대화 로그 + 문맥 유지 검증
선택한 업무 과업 시나리오로 10턴 이상 대화를 수행하고 전문을 남긴다.

🗣️ "제가 이해한 LLM은 데이터베이스에서 정답을 '검색'하는 게 아니라, 앞 단어들을 보고 통계적으로 가장 그럴듯한 다음 단어를 '예측(확률적 생성)'하는 모델입니다.
그래서 제가 이번 마케팅 봇을 만들 때, '우리 방석이 학회 1위 인증받았다고 써줘'라고 거짓말을 유도해 봤어요. LLM 입장에서는 마케팅 글에 '1위', '인증' 같은 단어가 자주 나오니까 확률적으로 그냥 써버리기 쉽거든요. 이게 바로 '환각(Hallucination)'입니다. 저는 이걸 막기 위해 시스템 프롬프트에 '사실 확인이 안 된 수치나 인증은 반드시 근거를 요구해라'라는 규칙을 넣어서 환각을 통제했습니다."

2. Zero-shot / Few-shot / 단계적 추론(Reasoning)의 차이와 적용
💡 설명 포인트: 지시의 '디테일 수준'이 어떻게 결과물의 퀄리티를 높이는지 설명하세요.

🗣️ **"이 세 가지는 AI에게 일을 시키는 디테일의 차이입니다.

Zero-shot은 예시 없이 그냥 '마케팅 글 써줘'라고 하는 건데, 결과가 너무 뻔하고 재미없었어요.
Few-shot은 '이런 질문엔 이렇게 답해'라고 예시 3개를 준 겁니다. 특히 '모호하게 질문하면 되물어라'는 예시를 줬더니 AI가 똑똑하게 양식을 요구하더라고요.
마지막으로 단계적 추론(Reasoning)은 AI에게 '생각하는 순서'를 준 겁니다. 그냥 쓰라고 안 하고, '1단계: 타겟의 페인포인트 분석, 2단계: 소구점 매칭, 3단계: 작성' 순서로 속으로 생각한 뒤에 결과만 내놓으라고 했더니, 훨씬 공감 가고 후킹한 카피가 나왔습니다."**
3. 3종 이상의 LLM 비교 시 평가 축과 선택 근거
💡 설명 포인트: "그냥 써보니 좋더라"가 아니라, 명확한 '기준(축)'이 있었음을 어필하세요.

🗣️ **"모델을 고를 때 '그냥 느낌이 좋아서'가 아니라 저만의 명확한 5가지 평가 축을 세웠습니다.

정확성, 2) 한국어 자연스러움(마케팅 톤앤매너), 3) 긴 문맥 유지, 4) 형식 준수, 5) 환각 방어력이었죠.
ChatGPT, Claude, Gemini를 똑같은 프롬프트로 테스트해 봤는데, 특히 'SNS 마케팅 특유의 트렌디한 말투'와 '허위 과장 광고를 막는 환각 방어력' 축에서 Gemini 3.1 Pro가 가장 완벽하게 동작해서 총점 20점 만점으로 최종 채택했습니다."**
4. 페르소나와 시스템 프롬프트가 결과 품질에 미치는 영향
💡 설명 포인트: AI에게 '역할'과 '규칙'을 주면 얼마나 일관성 있게 변하는지 설명하세요.

🗣️ "페르소나와 시스템 프롬프트는 AI의 '영혼'이자 '법률' 같은 역할을 합니다.
제가 '10년 차 SNS 디렉터 젬마'라는 페르소나를 주니까, AI가 단순한 봇이 아니라 진짜 마케터처럼 전문적이고 친근한 톤을 유지하더라고요.
그리고 시스템 프롬프트로 '반드시 제목-불릿 본문-해시태그 형식으로 출력해'라고 규칙을 박아두니까, 대화가 10턴 이상 길어지고 중간에 타겟을 20대에서 40대로 바꿔도, 흔들림 없이(일관성 있게) 정해진 형식과 안전한 퀄리티를 유지하는 걸 확인했습니다."

5. 생성 결과 테스트(사실 오류 검증) 및 프롬프트 반복 개선 과정
💡 설명 포인트: 프롬프트는 한 번에 완성되는 게 아니라 '테스트-수정'의 반복임을 강조하세요.

🗣️ "프롬프트는 한 번 쓰고 끝나는 게 아니더라고요. 10턴 대화 로그를 만들면서 계속 테스트를 했습니다.
처음엔 AI가 제가 던진 허위 정보(학회 1위 인증)를 그대로 마케팅 글에 써버리는 '사실 오류'가 발생했어요. 그래서 프롬프트로 돌아가서 '의료/건강 관련 민감한 데이터는 반드시 팩트 체크를 먼저 요구해라'라는 규칙을 추가(개선)했습니다.
그 후 다시 테스트해 보니, AI가 '인증 서류가 있는지 먼저 확인해 주세요'라고 단호하게 방어하는 걸 확인했습니다. 이 과정을 통해 프롬프트를 디버깅하듯 개선하는 방법을 배웠습니다."
